# Spec: Canvas search results scroll and focus visibility (#11092)

## Goal

When canvas search returns many matches, the sidebar result list must stay within the panel: users can scroll through all rows, and the focused match must remain visible when moving focus with the navigation controls (and equivalent keyboard flows).

## Context

- Issue: [#11092](https://github.com/excalidraw/excalidraw/issues/11092) — long lists overflow or behave poorly; prev/next should not leave the focused row off-screen.
- Current problem (reported): results overflow the panel and/or focus navigation does not keep the active row in the visible scroll area.
- Expected: one clear scroll region for results; focused row scrolls into view when focus changes.

## Component / Module

- `packages/excalidraw/components/SearchMenu.tsx` — layout wrapper, `MatchList` ref map, `useLayoutEffect` + `scrollIntoView` on `focusIndex` / match list `nonce`.
- `packages/excalidraw/components/SearchMenu.scss` — flex/`min-height` for `.layer-ui__search`, scroll container `.layer-ui__search-results-scroll`, non-scrolling `.layer-ui__search-result-container`.
- `packages/excalidraw/components/Sidebar/Sidebar.scss` — `min-height: 0` on `.sidebar-tabs-root` and `[role="tabpanel"]` so nested flex children can shrink and scroll (sidebar tabs).

## Non-goals

- Do NOT virtualize the list or replace it with “current match only” UI (possible follow-up for very large result sets).
- Do NOT change search matching semantics, debounce timing, or canvas highlight logic beyond what is required for layout/scroll.
- Do NOT touch protected core files (`Renderer.ts`, `restore.ts`, `manager.tsx`, `types.ts`) for this fix.

## Acceptance criteria

1. When the combined height of result rows exceeds the space below the search field and counter row, the results area shows a vertical scrollbar (or equivalent) and every row can be reached by scrolling.
2. When the combined height fits, all rows are visible without clipping; scrollbar may be inactive.
3. When the user moves to the next or previous match via the search navigation controls, the newly focused row scrolls into view inside the results area if it was outside the visible viewport.
4. When the user selects a different row by clicking (existing behavior), the focused row scrolls into view if needed.
5. Frame vs text grouping, match counts, and existing keyboard handling for search (e.g. Enter / arrows while focus is in the search UI) continue to work as before.
6. Existing automated search tests pass; typecheck and app build pass.
